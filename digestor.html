핵심 시스템

서버 권위 네트워킹

Netcode for GameObjects와 Unity Relay로 서버가 게임 상태를 판정하고, 이동만 오너 클라이언트가 냅니다. 판정은 물리 콜백(OnTriggerEnter 계열)을 하나도 쓰지 않고 SphereCast·OverlapSphere로 매 프레임 검사해, 네트워크 동기화와 콜백 타이밍이 어긋나는 버그를 설계 단계에서 막았습니다.

  1. 클라이언트 (오너)

    입력, 이동

    도구 사용은 요청만 보냄

  2. 서버 (Relay 호스트)

    판정, 상태 결정

    SphereCast·OverlapSphere 매 프레임 검사

  3. 모든 클라이언트

    결과 동기화, 연출

    2~4인이 같은 결과를 봄

보스 그로기: 팀이 딜 창을 만든다

코어가 열리는 시간을 보스 스케줄에만 맡기면 팀이 할 수 있는 건 기다리는 것뿐입니다. 그래서 몸에 붙은 구슬을 두들겨 그로기 게이지를 깎으면 보스가 무너지는 구조를 설계했습니다. 기생충 보스는 3페이즈 상태머신으로 돌아갑니다.

폴백 세이프 아트 파이프라인

지형·소품은 코드가 절차 생성한 로우폴리 메시를 기본으로 두고, 블렌더 모델이 준비되면 슬롯에서 교체합니다. 모델이 없어도 게임은 항상 돌아갑니다. 들여온 음식·액세서리 모델은 아래처럼 단계별로 캡처해 확인했습니다.

개발 중 내린 엔지니어링 판단 세 가지

  1. 물리 콜백 0건 원칙에 예외를 하나만 둔 이유

    문제
    부서진 음식 조각(FoodPieceDebris)에 손수 만든 낙하 로직을 적용하자 조각이 공중에 멈추고, 바닥에서는 서로 파고드는 버그가 실제로 났습니다.
    대안
    레이캐스트와 반경 겹침 해소 로직을 계속 보완해 원칙을 지킬지, 문제가 난 음식 조각만 동적 리지드바디에 맡길지를 비교했습니다.
    선택
    실제로 동작하는 결과를 우선하되, 예외가 번지지 않도록 FoodPieceDebris 한 경우에만 동적 리지드바디를 허용했습니다. 이 조각은 NetworkObject가 아니고 서버가 위치를 정하지 않아 금지의 근거가 해당하지 않습니다.

  2. 보스 크기를 높이가 아니라 몸 길이로 역산한 이유

    문제
    보스는 기어가는 바인드 포즈에서 4.0m, 몸을 세운 자세에서 6.4m로 높이가 달라, 한 자세를 기준으로 잡으면 다른 자세의 크기가 어긋났습니다.
    대안
    4.0m의 기어가는 자세와 6.4m의 세운 자세 중 하나를 높이 기준으로 삼는 방법과, 자세에 덜 흔들리는 몸 길이를 기준으로 삼는 방법을 비교했습니다.
    선택
    높이 대신 몸 길이를 기준으로 잡고, 납품 규격 전장 20m를 아레나에서 존재감이 나오는 40m로 키운 값에서 스케일을 역산했습니다. 자세가 바뀌어도 크기가 일관되게 보입니다.

  3. 임포터 캐시로 코드 수정이 조용히 안 먹던 문제를 잡은 과정

    문제
    스케일 커브 규칙을 고친 뒤에도 임포터 버전이 그대로여서 며칠간 캐시된 옛 결과가 쓰였고, 캐릭터 애니메이션 클립 43개가 모두 낡은 상태였습니다.
    대안
    필요할 때마다 강제 재임포트를 기억해서 실행할지, 임포터 코드가 바뀔 때 버전 번호도 함께 올려 캐시를 무효화할지를 비교했습니다.
    선택
    AI 도구와 함께 강제 재임포트 때 유니티가 낸 불일치 경고를 따라가 원인을 찾았고, 같은 문제가 조용히 반복되지 않도록 임포터를 고치면 버전 번호를 반드시 올리는 규칙을 AI 도구가 매번 읽는 프로젝트 지침 문서에 적었습니다.

설계·구현·검증을 나눈 개발 방식

한 에이전트에 모든 판단을 맡기지 않고 구현 전후의 검토 역할을 나눴습니다. 이 에이전트들은 사람 팀원이 아니라 기획·프로그래밍 작업에서 쓴 도구입니다.

  1. Claude Code

    설계, 통합, 최종 검토

    전체 설계를 세우고 결과를 통합

  2. Codex

    구현

    범위를 좁힌 쓰기 권한만 부여

  3. verifier

    구현 후 검증

    구현자와 검증자를 나눠 같은 맹점 차단
